# L2C: From Plans to Shop Drawings. Design Spec

Date: 2026-10-03. Status: draft for review. Authors: Eric (backend/ML), Ian (frontend), Chandler (pitch).

## 1. Goal and success criteria

Automate verification of reinforcement shop drawings (dessins d'atelier, "DA") against structural plans. Given a project's plan PDF and shop-drawing PDFs, produce:

1. A JSON database of every identified reinforcement annotation (official Appendix A schema), with sheet and X/Y.
2. A match between each plan element and its shop-drawing equivalent.
3. A classification per element: `compliant`, `non_compliant` (with detailed diffs), `missing` (in plan, not in shop drawings), `added` (in shop drawings only).
4. A PDF report per plan sheet: conformity and non-conformity counts, plus a detailed discrepancy list.
5. A working application (CLI + Streamlit) that takes a project directory and produces 1 to 4.

Scoring (from the official brief): non-conformity detection 30 (recall weighted above precision), extraction and JSON quality 20, report usefulness 15, code quality 15, robustness on an unseen project and all five element types 10, presentation 10. The evaluation project is hidden and contains known, documented non-conformities.

Primary design consequence: **a missed non-conformity costs more than a false alarm.** Every uncertain case becomes `needs_review`, never a silent pass.

### Hard constraints
- Python core. JSON output conforming to the schema. PDF report.
- No document may be sent to a cloud service or external AI API. All OCR/ML runs locally. Data is deleted from workstations after the event.
- No commercially licensed software the jury cannot run. Dependencies in `requirements.txt` or `pyproject.toml`; clear entry point.
- Data never enters git. `data/` contents are gitignored. No raw drawing text in committed docs, tests or logs.
- Deliverables: repo, `.ipynb` (exploration + end-to-end demo on one project), model weights and training script if any model is trained, app/CLI, README, 10-minute live demo on the evaluation project, generated JSON and PDF for the provided projects.

## 2. Data findings (discovery, read-only)

Four development projects (names are folder names): CLP, LIGREP, WP2, EspCa3B. Each has one multi-page plan PDF (`L2C_PLAN_STR_<project>.pdf`, 28 to 72 pages) and a `DA/` tree of shop-drawing PDFs grouped by element type (Colonnes, Poutres, Dalles, Fondations, Refends/Murs). CLP additionally ships `CLP_dismatch.xlsx`, listing 6 known discrepancies (columns: sheet, location, plan value, shop value), spread across foundation, wall, column and slab sheets. It is the only labeled ground truth.

Sheet series: S-100 foundation, S-300 beam, S-400 shear wall, S-500 column, S-600 slab (plus S-0xx general notes/details and S-2xx details, which also carry rebar annotations but are typical details, not project elements).

### 2.1 Text layer availability: the main risk
- **Plan PDFs**: native text layer on every sampled page. Pages are very large (about 1728x2592 up to 3455x2590 pt).
- **Shop drawings: mixed.** Some column sheets have real text and include bar-list tables (`QTY SIZE LENGTH WGT ... MARK TYP A B C D ...`). Many sheets (most EspCa3B, many slab/foundation/wall sheets in LIGREP and WP2) return effectively zero characters. Text is either outlined as vector paths or sits in embedded raster images (WP2 and CLP slabs, some columns).

Consequence: **OCR on rasterized pages is a core path for shop drawings, not a fallback.** The pipeline detects per page whether a usable text layer exists and routes accordingly (section 4.1). Any claim in earlier brainstorming that "native text means no OCR" is withdrawn.

### 2.2 Notation shapes (digits masked; imperial units)

Plan, columns: `ARM.: #-#M` (count-size), `LIG.: #M@# c/c` (tie size @ spacing in inches), `BÉTON: #MPa / <class>`, sometimes `+ GOUJ.` (dowels). One block per column, repeated across a level.
Plan, beams: `# - #M` stacked rows, `RANG # : #-#M`, `#M @ # c/c`, `ARM. DE PEAU` (skin reinforcement), stirrups as `#M @ # c/c` groups per zone.
Plan, walls: `ARM: #-#M`, `V.:#M@#mm c/c`, `H.:#M@#mm c/c` (note: mm here), `LIG.: #M@# c/c`, `CA. #(#)x#(#)` (boundary-element style).
Plan, slabs/foundations: `#(#)`, `#(#)-#M`, `#-#M`, `RANG #`, `XX@YY` placeholders, `As min.: #M@#mm c/c`. The `#(#)` form (for example "16(8)") is used in the known-discrepancy list; parsed as count `N` plus secondary `M` (see section 10, Q1).
Shop drawings, columns (text layer): `VERT: # #M <mark>` and `ÉTRI: # #M <mark> @#"` where the first number after the label is a bar count and `<mark>` encodes size and shape. Marks do **not** equal plan element IDs.
Units: sizes are Canadian metric bar designations (10M, 15M, 20M, 25M, 30M, 35M). Spacings are in inches (`6"`, `12"`) on most sheets, in mm on some wall annotations. Elevations are in feet-inches. A unit normalizer is mandatory.

### 2.3 Locations are grid coordinates
The known-discrepancy list locates items by structural grid (letter row, number column, sometimes with decimals such as `10.8`) or by named elevation. Grid labels appear as text on the plan sheets. This gives a mark-independent matching key (section 4.3).

## 3. Approach

Chosen approach: **deterministic backbone, grid-anchored matching, small learned components, local VLM only for low-confidence regions.** Rejected: pure rules (brittle on the hidden project, no ML story), and vision-first YOLO/OCR-everything (native text exists on plans, annotation cost, hurts recall).

Delivery is split into two explicit phases. Phase 1 is a slow, rough MVP that works end to end. Phase 2 is the optimized, precise version. Phase 1 must exist before phase 2 starts replacing parts. Cut rules from CLAUDE.md apply: stretch items are cut without debate when behind.

## 4. Architecture

```
project dir (plan.pdf + DA/**/*.pdf)
  -> ingest   -> words/bboxes per page (+ raster for no-text pages)   [cache]
  -> extract  -> Appendix A elements (plan and shop), per element type
  -> match    -> plan element <-> shop element pairs
  -> compare  -> findings (compliant/non_compliant/missing/added/needs_review)
  -> report   -> per-sheet PDF + findings.json + elements.json
  -> app      -> Streamlit review UI; CLI `l2c run <project_dir>`
```

Each stage reads and writes JSON files, so any stage can be mocked or rerun independently and Ian can build the UI against fixtures from hour one.

### 4.1 `ingest`
- PyMuPDF opens each PDF. Per page: `get_text("words")` yields words with bboxes in PDF points (top-left origin, as the schema requires). If a page has fewer than N text chars (threshold tuned empirically), mark `needs_ocr`.
- For `needs_ocr` pages: render at a fixed DPI in tiles (pages are huge; full-page rasterization is too big for OCR). Tile size about 2000 px with 10% overlap. Run OCR per tile, map boxes back to PDF points, deduplicate overlap boxes.
- Outlined-vector text: first try the glyph decoder (section 10.1, item 1); rasterize plus tiled OCR is the fallback and the default if the decoder spike fails its 90-minute check.
- Cache: `data/cache/<project>/<file>/<page>.json` (words, bboxes, source=`text|ocr`, per-word confidence). Parse each PDF once.
- Parallel: page-level `multiprocessing` after phase 1 works.

#### 4.1.1 OCR engine benchmark (first hour, on 3 to 5 pages)
Candidates: PaddleOCR (pip), Tesseract (brew), EasyOCR. Metrics: recall of tokens matching the rebar regexes (`\d+\s*-\s*\d{2}M`, `\d{2}M\s*@`), seconds per tile, setup pain. Decide once, record in README. OCR is behind an interface `ocr(tile) -> [Word]` so it is swappable.

### 4.2 `extract`
Output record is the Appendix A schema exactly (`id, source, fichier, feuillet, page, x, y, type_element, element, armature[]`) with optional extra fields: `confidence` (0 to 1), `grid` (e.g. "K-6"), `level`, `bbox`, `raw_text`, `extraction_method` (`regex|classifier|vlm`). Extra fields must not break schema validation (Pydantic model with the optional fields; the strict official schema is validated separately by exporting without extras).

**Phase 1 method (rules):**
1. Normalize tokens: merge split tokens into logical statements by Y proximity and X order (so `10M`, `@`, `6"` become `10M @ 6"`).
2. Regex library, one module per notation family (count-size, size@spacing, mm and inch spacing, `N(M)`, mark+size, QTY tables).
3. Block builder: for each anchor (an `ARM.:` line, a `VERT:` line, a bar-list row), collect statements within a radius and within the same drawn detail, producing one element.
4. Sheet-level typing: sheet series number picks `type_element` (S-100 foundation, S-300 beam, S-400 wall, S-500 column, S-600 slab). Shop-drawing file/folder name gives the type for DA files.
5. Unit normalization: spacing to `espacement_mm` (inches times 25.4), bar length in mm, count as int.

**Phase 2 additions:**
- **Token-role classifier.** Features per token: regex hits, geometry (relative offset to anchor, row/column alignment), font size/rotation when available, neighbor tokens, page region. Model: LightGBM or small gradient-boosted trees (CPU, trains in seconds). Labels come from phase-1 rule output on LIGREP and WP2 (weak supervision), spot-corrected by hand. It replaces brittle radius thresholds for associating values with the right element and catches variants the regexes miss.
- **Local VLM fallback** (Qwen2.5-VL or similar via MLX or Ollama; the team's M4 with 24 GB is the target machine). Invoked only on blocks with confidence below a threshold, with a cropped image plus OCR text, and a JSON-only prompt. Its output goes through the same regex validators; anything non-conforming is marked `needs_review`. Never used as the comparator. Never required: with VLM off, the pipeline still completes.
- **Bar-list tables** (QTY/SIZE/LENGTH/MARK) in shop drawings give counts per mark directly. Parse them as tables (column x-alignment) as an independent second source to cross-check counts from annotations.

### 4.3 `match`
Goal: pair each plan element with its shop-drawing equivalent. Marks differ between the two, so identity comes from **location**, not names.

1. **Scope match** (cheap, exact): plan sheet series plus level/elevation text to DA file/page (a column plan for level 2 matches the shop file for the corresponding level range). A learned or hand-written lookup from DA file names (`NIV 2`, `RDC@2`, `FDN@RDC`) to level ranges. Failures go to `needs_review` at sheet level.
2. **Grid recovery** per sheet: detect grid labels (letter and number sequences along the sheet edges, plus their positions), fit axis lines, and map any (x, y) to a grid cell `(row, col)` with fractional offsets (the `10.8` case). Done for plans and for shop drawings that carry a grid. Reconcile the two grids by label, not by coordinates.
3. **Element match**: key = `(type, level, grid cell)`. Cost matrix over candidates in the same scope: grid distance first, then attribute agreement as a tie-breaker; Hungarian assignment (`scipy.optimize.linear_sum_assignment`) with a max-cost cutoff. Unmatched plan elements become `missing`; unmatched shop elements become `added`.
4. **Phase 1 fallback:** if grid recovery is not ready, nearest-neighbor in normalized page coordinates after aligning the two drawings by their common grid labels or bounding boxes. Coarse but works on columns.
5. Typical (repeated) columns and details: a plan note can apply to many elements ("TYP."). Expand typicals only when a rule is explicit; otherwise flag `needs_review`.

### 4.4 `compare`
Deterministic. For each matched pair, compare `quantite` (primary), `diametre`, `espacement_mm`, `longueur_mm`, only fields present on both sides. Tolerances: spacing within 1 mm after unit conversion, length within 5 mm (configurable). Output `findings.json`:

```
{ status, type_element, feuillet, plan_ref: {id,page,x,y}, shop_ref: {...},
  diffs: [{field, plan, shop}], confidence, notes }
```

Confidence combines extraction confidences and match cost. Rule: status is `compliant` only if both extractions and the match are above thresholds; otherwise `needs_review`. The threshold is a single knob tuned for recall.

### 4.5 `report`
ReportLab PDF, one section per plan sheet: counts of compliant / non-compliant / missing / added / needs_review, a table of discrepancies (element, grid location, field, plan value, shop value, source page and X/Y so the engineer can find it). Summary page first. Phase 2: annotated sheet thumbnails with circles at the flagged X/Y on both plan and shop drawing (bonus), plus links between the two. Every element type appears in the report; types with no coverage are stated explicitly, which supports the "transparency about limits" scoring.

### 4.6 `app`
- CLI: `python -m l2c run <project_dir> --out <dir>` produces `elements.json`, `findings.json`, `report.pdf`.
- Streamlit: pick or upload project, run with progress, browse findings by sheet, filter by status, view source crop (rendered region) next to plan crop, mark reviewed / false positive (bonus: confidence-based review of uncertain cases). Ian owns this. It reads only the JSON contract.

## 7. Evaluation and testing

**Data split (decided):**
- Develop parsers and train/tune on LIGREP and WP2 (CLP for column structure).
- **CLP**: labeled test set. Its 6 known discrepancies must be found. Not used for tuning thresholds beyond sanity.
- **EspCa3B**: blind generalization test, touched in the last hours only. It is also the hardest for text layers (mostly no text), so it stresses OCR.
- The hidden jury project is the real test; the system must not depend on project-specific constants.

**Metrics:** recall and precision of non-conformities on CLP; extraction completeness (fraction of regex-visible annotations captured); schema validity rate; end-to-end seconds per project.

**Mutation tests (synthetic):** take clean matched pairs, perturb one attribute (count +/-1 to 2, spacing swap, diameter swap, delete, duplicate), and assert the comparator and matcher flag it. Gives unlimited labeled cases without touching confidential labels.

**Unit tests:** unit normalizer, each regex family against masked/synthetic strings (no real values in the repo), grid mapper on synthetic grids, Hungarian matcher on constructed cases, schema validation of every output.

**Smoke test:** `scripts/smoke_test.sh` runs the demo path on one project end to end. Run every ~3 hours (CLAUDE.md).

## 9. Risks and mitigations
1. **No text layer on many shop drawings** (biggest). Mitigation: OCR benchmark in hour 1, tile-based OCR, columns first, report states coverage honestly.
2. **Plan-to-shop matching without shared IDs.** Mitigation: grid-anchored key, Hungarian assignment, `missing`/`added`/`needs_review` rather than wrong pairs.
3. **Unknown meaning of some slab notation** (`#(#)`). Mitigation: parse `N(M)` as count plus secondary (section 10, Q1); compare `N` primarily, flag mismatches in `M` as `needs_review`.
4. **Huge pages make OCR slow.** Mitigation: tiling, caching, only OCR pages that need it, page-level parallelism.
5. **Generalization to the hidden project.** Mitigation: no project constants, blind EspCa3B test, VLM fallback, recall-biased `needs_review`.
6. **VLM speed/quality.** Mitigation: optional and off by default; only low-confidence blocks.
7. **Confidentiality.** Mitigation: nothing leaves the machine, `data/` gitignored, no real values in tests or docs, delete data after the event. Note: during planning, short snippets of plan and shop-drawing text were viewed in the AI assistant session; the team lead stated this was approved. Going forward, prefer local scripts that output aggregates.

## 9.1 Dataset inspection results (all 141 PDFs, 611 pages, profiled locally)

Plan PDFs: 190 pages, all with a native text layer. Shop drawings: 421 pages, page size almost always about 2500 x 1700 pt (388 of 421); some pages have rotation 90, 180 or 270, so rotation handling is required, not optional.

Shop-drawing layer type by project (pages):
| Project | Colonnes | Dalles | Fondations | Poutres | Refends |
|---|---|---|---|---|---|
| CLP | text 13 | text 18 | text 2 | text 1 | none supplied |
| LIGREP | text 40, vector 11 | vector 124 | vector 11 | text 1, vector 2 | vector 2 |
| WP2 | image 33, vector 3 | vector 30 | vector 4 | none supplied | vector 2 |
| EspCa3B | vector 22, image 1 | vector 91, image 2 | vector 6 | none supplied | vector 2 |

Overall: **17% text, 73% vector-outlined, 8% embedded images.** Consequences:
- **CLP is fully text-layer on the shop side and carries the labeled discrepancy list. It is the MVP development project and can cover columns, slabs, foundations and beams without OCR.**
- LIGREP columns are mostly text, everything else is vector. WP2 columns are images. EspCa3B (our blind test) is entirely vector.
- The hidden evaluation project is likely to look like the majority (vector or image). So the no-text path is required for generalization and cannot be a stretch item.
- Beams and walls have almost no shop data in the development set (1 text beam page, 6 vector wall pages across projects). Coverage for those types will be thin and tested mostly with mutations.
- Bar-list tables (`QTY`) appear on 40 LIGREP pages; `VERT`/`ÉTRI` lines on 68 pages (CLP, LIGREP); `requis` slab lines on 14 CLP pages.

### OCR and glyph experiments (decisions)
- **Exact glyph-shape hashing is rejected** as the main method. Even with a scale-normalized key, a vector page had 850 to 2700 unique shapes and the top 150 shapes covered only 36% to 62% of small filled shapes. Glyphs are not identical vector sequences. Demoted to a research idea, not planned work.
- **Local OCR works well enough with tuning.** RapidOCR (ONNX, pip only, CPU) reads vector pages at about 1.5 s per 2000x1400 px tile (150 dpi). Measured against native-text ground truth on text-layer sheets, recall of bar-size tokens and spacing tokens was: 93 to 100% (LIGREP sheet), and, after trying page orientations 0, 90 and 270 and summing, 96% sizes and 100% spacings on the CLP sheet (a single orientation gave only 12 to 52% on sizes because the page is rotated). Recall only; precision still to measure. A first untuned strict-string check scored lower (25 to 54%), which shows the metric and the orientation handling matter.
- **Techniques to adopt:** detect page orientation once (use the page rotation attribute, confirm on one probe tile) instead of running three orientations on every tile; skip blank tiles using vector-path density; render at 200 to 220 dpi for small text; **vocabulary snapping** (sizes snap to {10M, 15M, 20M, 25M, 30M, 35M}, spacings to the observed small set, counts to plausible ranges) and cross-check OCR against totals where a bar list exists.
- **Cost model:** about 9 tiles per page at about 1.5 s is roughly 14 s per page single-threaded; 120 vector pages across 8 processes is about 3.5 minutes. That fits the 5-minute budget only if orientation is detected once and blank tiles are skipped. Do not run all three orientations on every tile in the live path.
- **Priority change:** OCR path moves from SHOULD to **MUST for generalization (phase 2, first item)**. Glyph decoder is cut. A final MVP gate stays on CLP (text only).

### Revised MVP scope
MVP = CLP end to end for every element type that has shop data there (columns, slabs, foundations, beams), plus LIGREP columns. This is larger in element types than "columns only" but cheaper per type because no OCR is involved, and it is testable against the CLP labeled list (which spans foundation, wall, column and slab sheets).

## 10. Resolved questions (from data and research)

- **Q1, slab notation `N(M)` (resolved enough to build).** On slab plans it is used with strip notes ("RANG 1 to 4", "perpendicular to the edge is always rang 4") and a sheet default ("typical reinforcing bar (S.I.C.): <size>"), and appears next to or instead of `N-<size>`. The known slab discrepancy changes only `N` and keeps `M`. Decision: parse as `quantite = N` plus `secondaire = M`, compare `N` as the primary count and `M` as secondary, and apply the sheet default bar size when none is written. The exact physical meaning of `M` stays unverified; do not claim it in the pitch. Shop slab sheets use bar-list lines of the form `<label>: <qty> <size> <length ft-in> @<spacing>" (<n> long) (<k> requis)`, where `requis` is the required count. Web search found no public convention for `N(M)`.
- **Q2, level spans (resolved).** Yes. Shop file names encode level ranges (`NIV-2@3`, `RDC@2`, `FDN@RDC`). Plan column sheets are per level. A shop column file covers the storey between two levels, so scope match is level-N plan sheet to the DA file whose range starts at N. Lookup is built by parsing names with a regex plus the elevation text on the shop sheet.
- **Q3, TYP (resolved).** Column plans carry no TYP expansion rule; each column has its own block. Slabs use "S.I.C." defaults, which we expand (default size). Other TYP details (series S-2xx) are typical details, not project elements: extracted as `type: detail` and excluded from conformity counts.
- **Q4, missing/added (decision).** The brief classifies them as findings. Recall is scored on documented non-conformities, which in the one sample we have are all value differences. We report `missing` and `added` in the report, ranked below value diffs, and let a CLI flag choose whether they count in the headline non-conformity number (default: counted, because a missed one costs more).

## 10.1 Differentiators (unique to this solution)

Everyone will diff plan against shop drawing. We win by treating verification as **triangulation**: independent evidence sources fused into one recall-biased score, plus an extraction trick that removes the OCR bottleneck.

1. **[Rejected after spike, see 9.1] Glyph decoder for outlined text (no OCR).** Shop drawings with outlined text still contain the same glyph shapes thousands of times. Spike result: a crude shape key already puts 35 to 49 percent of small filled shapes into 40 clusters, and a page parses in about 0.2 s. Plan: robust shape key (scale/rotation normalized, handle stroked glyphs), cluster glyph shapes across all pages of a project, label each cluster once (about 40 symbols) by template matching against rendered font glyphs or one OCR call per cluster, then decode every word exactly by clustering glyph positions into lines. Result: exact text, no per-page OCR, orders of magnitude faster, deterministic, trivial to explain. OCR stays as the fallback for image-embedded pages and for failures. Fall-back rule if the spike does not reach 90 percent clean decode in the first 90 minutes: cut it and use tiled OCR.
2. **Triangulated verification.** A finding gets evidence from up to four sources:
   - Plan versus shop diff (the standard check).
   - Shop-drawing internal consistency: bar-list totals (`Total for size ...`) versus the sum of annotated counts on the same sheet. Catches shop errors even when matching fails.
   - Pattern anomaly: columns repeat across levels and within a level; a value that deviates from its peers is suspicious (majority vote, then isolation-forest style score). Boosts recall when matching is uncertain.
   - Engineering plausibility: code-style limits (for example tie spacing relative to bar diameter, bar count that physically fits the section, minimum clear spacing). Flags impossible values, which also guards against extraction errors.
   Fusion score drives `compliant` / `needs_review` / `non_compliant`. The report shows which sources agreed ("2 of 4 sources flag this").
3. **Impact estimate.** Convert each discrepancy to a steel weight and percentage change (bar length times unit mass per size; Canadian M-bar masses are public). Rank findings by structural criticality and weight so the engineer reviews the worst first. Pitch line: "not just where they differ, but how much it matters".
4. **Engineer-ready output.** Annotated plan and shop sheets with circles and cross-links, plus a one-line review comment per finding written from a template (local LLM only if time permits, templates first).
5. **Live learning in the review UI.** Reviewer accept/reject decisions update the confidence calibration during the demo (logistic regression on fusion features), so the system visibly gets sharper. Also yields precision numbers on stage.
6. **Revision compare** (official bonus) comes almost free: run the same extractor on two shop-drawing revisions and diff the element sets.
7. **Natural-language query over the JSON** ("columns on level 3 where tie spacing deviates") with a local LLM; cut first when behind.

Priority order for build: 1 (spike first), 2 (internal consistency and pattern anomaly cheap, plausibility next), 3, 4, 5. Items 6 and 7 are stretch.

## 10.2 Gap review (second pass)

### Verified by probe
- **Sheet ids** can be read from the title block (bottom-right `S-###` word): 26 of 28 pages on CLP and 38 of 40 on LIGREP. The known-discrepancy sheets (S-050, S-100, S-400, S-502, S-504, S-603) all exist as plan pages. Pages without a title-block id are cover or notes pages; treat as `feuillet = null` and skip.
- **Plan grids are recoverable**: grid letters and numbers are text and aligned along sheet edges.
- Page rotation is 0 on all sampled plan pages; still normalize rotation and cropbox in `ingest` so X/Y stay top-left.
- Repo is private. Python 3.9 is the macOS default and too old for some ML packages: pin Python 3.12 and use `uv` (installed).

### Corrected assumption: shop drawings do not reliably carry a grid
One CLP shop column sheet contained grid numbers but no grid letters; another LIGREP sheet had both. So matching cannot assume a full grid on the shop side. Revised matching key: `(type, level, row letter, column number)`, where the row letter comes from the sheet title or detail label (column elevations are usually drawn per grid line) and the column number from the grid labels on the elevation. If the row cannot be read, fall back to ordered sequence alignment of columns along the line (plan order vs shop order, using `Hungarian + monotonic constraint`). Beams, walls and foundations span grid cells, so their key is a grid span (start line to end line) or a named elevation. **Their shop-drawing notation has not been examined at all yet.** Task 0 for each element type is a 30-minute matching spike on real pages before writing its comparator.

### Additions to the design
1. **Derived-quantity check.** Plans give tie spacing; shop drawings give tie count (`ÉTRI: <count> <size> @<spacing>"`). Expected count is roughly storey height divided by spacing. Check that count and spacing agree with each other and with the plan: catches inconsistencies a pure field-by-field diff misses. Same idea for bar-list lengths in feet-inches.
2. **De-duplication.** One element can be annotated in several views (plan, elevation, section). Collapse duplicates by `(type, level, grid key, values)` before matching, otherwise extra copies become false `added` findings.
3. **Output in the jury's style.** The known-discrepancy list uses `sheet, location, plan value, shop value`. Findings export includes exactly those columns (CSV/XLSX) in addition to JSON and PDF, so the jury can compare ours to theirs without translation. Location uses grid notation (for example `K-6`) first, X/Y second.

## 10.4 Principles and the metadata layer

### Right tool, not AI by default
Every component defaults to the simplest deterministic method. An ML component is admitted only if it measurably beats the rules baseline on our test sets (CLP labels, mutation tests, blind EspCa3B); otherwise it is cut. We keep an ablation table (rules only, plus classifier, plus VLM) and show it in the pitch: it demonstrates engineering judgment and gives honest numbers.

| Job | Method | Why |
|---|---|---|
| Text and coordinates from PDF | PyMuPDF, no ML | exact, instant |
| Text from outlined vector glyphs | glyph-shape clustering (no ML), OCR fallback | exact when it works |
| Reading notation (`4-25M`, `10M@6"`) | regex plus unit normalizer | deterministic, testable |
| Associating values to elements | geometry rules first; small classifier only where rules measurably fail | cheap, explainable |
| Matching plan to shop | grid key plus Hungarian assignment | optimal, no training data needed |
| Comparison and tolerances | deterministic rules | engineers must trust it |
| Pattern anomaly | majority vote / robust z-score | simple statistics beat a neural net on tiny data |
| Confidence calibration | logistic regression on reviewer decisions | small, interpretable |
| Unreadable blocks | local VLM, optional, low-confidence only | last resort |
| Review comments | templates | no hallucination risk |

Note: this makes the "ML" share modest. That is intentional. The learned parts that remain (OCR fallback, token-role classifier, anomaly scoring, calibration, VLM fallback) are real and measured. Never let a model make the final conforming/non-conforming call without a deterministic check behind it.

### ML budget (included on purpose, bounded on purpose)
ML is part of the product, but each piece has a job rules cannot do well, a time box, a kill criterion and a rules fallback. Total ML budget is about 3 hours of the night, started only after phase 1 works. All pieces train on weak labels produced by our own rules plus the mutation generator, so no manual labeling and no dependence on the 6 known discrepancies.

| ML piece | Job | Data needed | Time box | Kill criterion (cut if) | Fallback |
|---|---|---|---|---|---|
| Pretrained OCR (PaddleOCR or Tesseract) | read image-embedded pages | none (pretrained) | 45 min | below 90% recall on rebar tokens | glyph decoder, or mark `needs_review` |
| Token-role / association classifier (LightGBM) | attach count, size, spacing to the right element when layout is irregular | weak labels from rules on LIGREP and WP2 | 60 min | does not beat rules on held-out pages | geometry rules |
| Calibrated fusion score (logistic regression) | combine the 4 evidence sources into one confidence; update from reviewer clicks | mutation tests plus reviewer decisions | 45 min | not better calibrated than a fixed threshold | fixed thresholds, recall-biased |
| Anomaly scoring (isolation forest or robust z-score) | flag values that deviate from peer columns | none (unsupervised) | 30 min | adds false alarms without catching mutations | skip source 3 |
| Local VLM (optional) | unreadable blocks only | none (pretrained) | 30 min | slower than 20 s per block or inaccurate on a spot check | `needs_review` |

Guarantee we commit to: at least the classifier and the calibrated fusion/anomaly scoring ship with measured gains, plus pretrained OCR where needed. Each is reported in the ablation table (rules only versus plus-component) on CLP and mutation tests. If a piece is killed, we say so in the pitch with its numbers; that is transparency the jury scores.

### Metadata layer (the product's core)
Goal: transform the raw PDFs once into a canonical, queryable model, and let everything else consume only that.

Stored per project under `data/out/<project>/` as plain JSON (no extra infrastructure; load into pandas for compare):
- `sheets.json`: sheet id, page, file, revision, scale text, type.
- `grid.json`: per sheet, gridline labels and positions; per project, reconciled grid in real units (mm).
- `levels.json`: level names and elevations (mm), parsed from `EL.: 157' - 9"` style text.
- `elements.json`: Appendix A records plus: `grid`, `level`, `section` (for example 16x24 in, parsed from `COL. 16"x24"`), `elevation_range_mm`, `bbox`, `confidence`, `extraction_method`, `raw_text`, `provenance` (file, page, bbox) for evidence crops.
- `matches.json`: plan id, shop id, cost, method.
- `findings.json`: statuses, diffs, evidence sources, impact (kg, percent).

Rules: every value carries provenance back to a PDF region; geometry is stored in real units (mm) in addition to PDF points; schemas live in `shared/`. UI, report, XLSX export and the 3D model are pure functions of these files. Because of that, they can be developed against fixtures and re-run without reprocessing PDFs.

## 10.5 Extra: 3D building view (COULD tier, after MUST and SHOULD)

Concept: a 3D model of the building generated from the metadata; clicking a discrepancy flies the camera to that element, highlights it, and shows the plan rebar versus the shop rebar so the engineer sees what to fix.

Feasibility from the data seen: grid labels and scale text ("1/8" = 1'-0"") convert PDF points to real units; level elevations are text; column sections are text; walls and beams have grid spans; slabs cover grid bays. Enough for a schematic (not survey-accurate) model: columns as prisms at grid intersections between levels, walls as slabs between grid lines, beams as bars between supports, floor plates per level. Rebar view for the selected element: draw the longitudinal bars in the section (count and size) and ties at the stated spacing, plan in one colour and shop in another, difference highlighted.

Design: backend writes `model3d.json` (levels, grid, element boxes with ids that match `elements.json`, optional rebar spec per element). Frontend renders with three.js (Ian's lane, a Streamlit custom component or a small static page the app embeds); selection is by element id, so it plugs into the review list. No server work beyond writing one file.

Requirements to keep this cheap: extraction already stores grid, level, section and real-unit coordinates (section 10.4), so no rework is needed later. Start only after: columns end to end, report, and at least beams and walls extracted. Hard cut at 4 AM if not clearly working, because the review UI and report carry the score. Do not describe geometry as exact in the pitch: say "schematic model from drawing data".

### Scope of the MVP (phase 1)
Columns end to end on projects whose shop column sheets have a text layer (CLP and LIGREP samples). Other element types and image/outline-only sheets are reported as "not covered", not guessed.

### Time estimate (Eric's backend lane, Claude-assisted coding, starting about 9 PM)
| Task | Estimate |
|---|---|
| Environment (Python 3.12 via uv), shared schemas, fixtures, smoke script | 45 min |
| `ingest`: PyMuPDF words, cache, title-block sheet id, rotation | 45 min |
| Column plan extractor (regex, block builder, unit normalizer) | 60 to 90 min |
| Column shop-drawing extractor (`VERT` / `ÉTRI` lines, bar-list tables) | 60 to 90 min |

Total: about 5.5 to 8 hours of backend work, so a working MVP lands at **about 2:30 to 4 AM**, not 1 AM. The 1 AM figure earlier is the optimistic case. Ian's parallel work (Streamlit UI, ReportLab PDF) takes about 3 hours and does not block Eric. If matching blows past 2 hours, ship the nearest-neighbor fallback and mark more items `needs_review`.

Budget view: MVP done by about 3:30 AM leaves about 2 hours for phase 2 priorities (beams, walls, one ML piece, annotations) before the 5 to 6 AM freeze. That is tighter than the original plan, so the tier order in 10.2 item 10 is binding: SHOULD items are cut to fit, never the MVP.

### Success criteria for the MVP (all must pass)
1. `python -m l2c run <project_dir>` finishes in under 5 minutes on one development project, exit code 0, and writes `elements.json`, `findings.json`, `report.pdf`.
2. 100% of output elements validate against the Appendix A schema.
3. Extraction completeness: at least 95% of column annotation blocks that a regex census counts on the column plan pages appear as elements with correct count and size. Verified by a script, plus a hand check of 20 random elements.
4. Matching: at least 80% of plan columns on text-layer shop sheets are matched; every unmatched element appears as `missing` or `needs_review`, never dropped.
5. Detection: both column-related discrepancies in the CLP known-discrepancy list are caught (100% recall on in-scope known items).
6. Mutation test: at least 95% of synthetic count, size, spacing, deletion and addition mutations are flagged.
7. Noise check: on one development project, hand-review 15 random `non_compliant` findings; at least 70% are real differences or genuinely ambiguous notation (the rest must have an understood cause, logged).
8. Report: counts per sheet add up to the totals; every finding lists sheet, grid location and X/Y; the PDF opens and is readable.
9. The smoke test passes twice in a row from a clean checkout.

### Success criteria for the full solution (phase 2 target, 5 to 6 AM)
- All five element types present in the report, each marked with a coverage statement.
- Recall on the CLP known list: goal 6 of 6, acceptable 4 of 6.
- Blind EspCa3B run completes without crashing and reports coverage honestly.
- Ablation table (rules only versus plus ML piece) filled in with real numbers.
- Notebook runs top to bottom; README states assumptions and limits.

## 10.7 Demo design (10 minutes, full flow shown live)

The rules ask for a 10-minute presentation with a live run on the evaluation project. The demo is the product shown end to end: upload, extraction, matching, findings, evidence, export. Nothing in it should be a slide pretending to be software.

### Timeline (target, rehearsed with a stopwatch)
| Time | What the audience sees | Who |
|---|---|---|
| 0:00 to 1:00 | the problem: engineer comparing PDFs sheet by sheet; stakes (rework, safety) | Chandler |
| 1:00 to 1:45 | one-slide architecture: PDF to metadata to checks, deterministic first, ML where it measurably wins | Chandler |
| 1:45 to 2:00 | **start the live run** on the evaluation project (drop the folder into the app) | Ian drives |
| 2:00 to 5:00 | **while it runs:** live progress, element counter climbing, sheets turning green; narrate what is happening per stage; text-layer pages appear first, OCR pages stream in after | Eric narrates, Ian shows |
| 5:00 to 7:30 | **findings walkthrough:** open the discrepancy list, click one, see plan crop beside shop crop with the exact values circled, confidence, evidence sources agreeing ("3 of 4"), steel-weight impact; mark one reviewed; export XLSX and PDF report | Ian drives, Eric explains |
| 7:30 to 8:30 | (if built) 3D view: click a discrepancy, fly to the element, plan rebar versus shop rebar | Ian |
| 8:30 to 9:15 | numbers: recall and precision on CLP, ablation table, coverage per element type, honest limits | Eric |
| 9:15 to 10:00 | takeaway, what is next, questions | Chandler |

Cut order if time or stability is short: 3D view first, then live-learning click, then impact numbers. The run, the findings click-through and the exports are never cut.

### Engineering requirements this adds
1. **Streaming pipeline.** The CLI and the app emit progress events (JSON lines: stage, file, page, counts, elapsed). The UI shows them live. Findings are written incrementally, so the list fills in while OCR pages are still processing.
2. **Fast pages first.** Order work so text-layer pages (cheap) are processed before OCR pages, so the first findings can appear within about 60 seconds.
3. **Time budget.** Complete run under 5 minutes on the evaluation project, first finding on screen under 60 seconds. Verified in rehearsal on the largest dev project (EspCa3B) with the cache cleared.
4. **Warm start.** OCR models loaded once at app start, not on first page. Python environment pinned (3.12 via uv) so launch is the same every time.
5. **Resumable and cached.** Cache keyed by file hash; killing and restarting the run reuses completed pages. The same mechanism powers the fallback.
6. **Fallback ladder (decided in advance):**
   1. Live run on the evaluation project.
   2. If it stalls beyond 90 seconds past the budget: say so, and switch to the cached run of a development project, then run the evaluation project in the background and show its results when done.
   3. If the app crashes: the recorded screen capture of a full run (made at 6 AM, short).
7. **Rehearsals.** At least two full 10-minute rehearsals with a stopwatch before presenting, including one with the fallback switch practiced. The first happens as soon as the MVP exists, the final ones after 7 AM with Chandler.
8. **Demo project folder.** Keep `demo/` (gitignored) with a prepared development project, its cached outputs and the recording, so the fallback is one click.
9. **Roles on stage.** Ian drives the UI, Eric explains technical choices and numbers, Chandler owns the story and timing and keeps the clock.
10. **Machine setup.** Demo laptop: charger, display scaling checked, notifications off, browser window pre-sized, no other heavy processes; test the projector resolution if possible.

### Added success criteria
- A scripted dry run of the 10-minute flow completes in 9 to 10 minutes twice in a row.
- First finding appears under 60 seconds and the full run completes under 5 minutes on EspCa3B with the cache cleared.
- The fallback switch is practiced at least once and takes under 20 seconds.
- Whatever the live result, the presentation states limits plainly (coverage per type, OCR confidence, items sent to `needs_review`); the rules score transparency.
